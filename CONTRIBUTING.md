# 🤝 Contributing

Thank you for your interest! 🙏 Reports are as valuable as code: a clear description of a problem often helps more
than a patch. English and French are both welcome 🇬🇧 🇫🇷.

If the repository has its own contributing guide (in its root, `docs/` or `.github/`), follow it: it comes first.

## 1. 💬 Start with an issue

Open an issue before writing code, so that we agree on what to do before you spend time on it:

- 🐛 **Bug**: what you did, what you expected, what happened, and the version. The smaller the example, the faster
  the fix.
- ✨ **Feature**: the need behind it, not only the solution you have in mind.
- ❓ **Question**: use the "Question" form.

Small fixes (a typo, a broken link) can go straight to a pull request.

## 2. 🔀 Pull requests

- **One pull request answers one issue.** Write `Closes #123` in the description so that the issue closes when
  the pull request is merged.
- Keep it small and focused: one subject, no unrelated reformatting.
- Branch from `main`, and keep your branch up to date with it.
- **Tests pass** locally and in the continuous integration. A bug fix comes with a test that fails without it; a
  new feature comes with its tests and documentation.
- Commit messages are in English, with a short summary line (`Date filter: keep the selected days first`) and,
  when useful, a body that explains why.
- Do not commit secrets, generated files or large data.

## 3. 👀 Review

Every pull request is reviewed by the maintainer, who may ask for changes before merging. Only the maintainer
merges. Some projects deploy automatically from `main`, so a pull request may wait for a good moment to go live.

If there is no answer after two weeks, a polite reminder in the pull request is welcome.
